### Дві особливості Ultralytics, знайдені й закриті

1. **Ultralytics сам доставляє пакети під час виконання.** Коли пакета бракує, він запускає
   `uv pip install …` прямо в `.venv`, повз `uv.lock`; так стається, наприклад, із `lap` для ByteTrack.
   Імпорт `sentinel` тепер ставить `YOLO_AUTOINSTALL=false`, і це покрито тестом.
   Відсутні ваги так само більше не завантажуються тихо: агенти падають з `FileNotFoundError`.
2. **Ultralytics сам керує потоками.** При імпорті він ставить `OMP_NUM_THREADS=1`, а під час першого predict —
   `torch.set_num_threads(8)`. Bench задає потоки після прогріву й записує фактичне значення.

  - частковий файл звірено як коректний префікс (побайтово з HTTP-діапазоном і через gzip/tar-потік);

- **Архіви лишено на диску:** 12,3 + 10,8 + 1,5 ГБ, бо повторне завантаження займає години.

Деталі до `schema.py`:
- округлення до 2 знаків, `-0.0` → `0.0`, щоб не ламати кеш LLM;
- NaN / inf і невідомі поля відхиляються;
- не більше 5 взаємодій;
- модель повністю незмінна (`frozen` + кортежі), бо A і B читають один об'єкт.

Деталі до `io/source.py`:
- `live` / `paced`: окремий потік тримає лише найсвіжіший кадр (черги немає), видача не частіша за частоту аналізу;

- збій джерела передається споживачеві винятком, а не вішає його;
- `"0"` відкриває вебкамеру;
- частота ≤ 0 відхиляється.

Деталі до `bench.py` / `cli.py`:
- прогрів окремим проходом;
- RTF міряється чесно: весь час обробки кліпу, включно з декодуванням усіх кадрів, / тривалість;
- рядки пишуться в JSONL, а звіт перегенеровується з нього;
- прогони на різних кліпах в один звіт не змішуються.

Тести: 53, моделі в тестах не завантажуються.
- Для відео — згенеровані MJPEG-кліпи з номером кадру, закодованим у яскравості.
- Для потоків — фейкова камера.
- Для bench — фейкові агенти з підставним годинником.

### Важливі зауваження

Усі виправлено через тести, які спершу падали й потім проходили (`4b57509`):
1. Збій у потоці читання камери вішав споживача назавжди → тепер виняток доходить до `read()`.
2. `--source 0` (рядок) трактувався як відсутній файл → відкривається вебкамера 0.
3. Опис сцени був незмінним лише поверхово (списки можна було змінити) → кортежі.
4. Звіт bench міг змішати прогони на різних кліпах під одним списком кліпів → відмова змішувати;
   версія OpenVINO записується в рядок.
5. Трек, чий скелет модель пропустила, міг отримати скелет сусіда (IoU ≥ 0,3 при половинному перекритті) →

### Відкладено

Це дрібні зауваження; більшість стосується `sentinel run` або наступних етапів.
- **Читач кадрів:**
  - `close()` без тайм-ауту;
  - немає перепідключення живого джерела;
  - облік на шляхах помилок;
  - `Frame` без монотонної мітки часу надходження (знадобиться для «затримки до тривоги»).
- **Трекінг і поза:**
  - номери треків ByteTrack спільні на процес (безпечно при одній камері на процес);
  - поріг NMS `iou` поза конфігом;
  - поза рахується і на кадрах без людей.
- **Bench:**
  - `timing([])` і кліп без кадрів падають;
  - `--threads` ігнорується при `--warmup 0`;
  - мітка `intel:gpu` при відкаті на CPU;
  - `clip_info` декодує кліпи при кожному рендері;
  - експорт OpenVINO не оновлюється при зміні `.pt`.
- **Схема:**
  - `RiskResult` приймає `"risk": true` і порожній `reason_uk` (сесія з агрегатором B);
  - правила §5 (відстань < 2 зростів, різні ID у парі, `t_start ≤ t_end`) не перевіряються.
- **Шляхи** рахуються від поточної теки (важливо для Docker).

## 7. Відхилення від SPEC

1. **Набір Севільї — кадри з частотою 2 кадри/с, а не відео.** §9 очікує «відео з камер зі зброєю»,
   але відеофайлів в офіційному джерелі немає.
2. **`Frame`, `Track`, `ReaderStats` — dataclass-и поза `schema.py`.** Це гарячий шлях із numpy-масивами.
   У pydantic лишаються контракти рівня опису сцени.
3. **Поза деревом §10 додано** `bench.py`, `tests/conftest.py`, `configs/bytetrack.yaml`.
4. **Режим `offline` синхронний**, без потоку, заради детермінізму експерименту. `live` і `paced` відповідають §6.
5. **Замір — лише на Fight-кліпах.** Це відхилення від промпту, не від SPEC: до NonFight архів тоді не докачався.

## 8. Рішення, які я ухвалив сам

| Рішення | Чому | Ціна, якщо неправильно |
|---|---|---|
| Системний Python 3.12.3 замість `uv python install` | уже був потрібної версії | жодна: Docker матиме свій |
| `uv.lock` лише під Linux | система працює на Ubuntu і в Docker | перегенерувати лок для іншої ОС |

| `conf 0.1` для трекера | ByteTrack використовує і слабкі детекції | більше слабких треків без скелета |
| Потоки torch задаються після прогріву | Ultralytics скидає їх на 8 під час налаштування предиктора | невірні мс/кадр, якби не зафіксувати |

| Прибрано стовпець «model RTF» | рахувався із середнього по двох прогонах і міг суперечити виміряному RTF | — |
| Пороги прив'язки скелета 0,8 / 0,5 / 10 % | обрано апріорі | треба перевірити на даних |
| `track_buffer: 30` залишено | значення Ultralytics; при 10 кадрах/с це 3 с, а не 1 с | підібрати на валідації |
| Завантаження з HF переведено з xet на HTTP; RWF-кліпи з задовгими іменами перейменовано детерміновано | xet зависав; ext4 не приймає імена > 255 байтів | імена 20 кліпів відрізняються від інших копій RWF |

## 9. Потрібні рішення

| № | Питання | Рекомендація |
|---|---|---|
| 1 | Залежність `lap` | **Додати в dependencies.** ByteTrack в Ultralytics без неї не працює (імпорт на рівні модуля, запасний шлях через scipy недосяжний). Зараз версія не зафіксована, а Docker її теж потребує |
| 2 | Розмір входу `imgsz` | **480** — див. пункти під таблицею |
| 3 | Модель людей і пози | **YOLO26n** — див. пункти під таблицею |
| 4 | Частота аналізу | **10 кадрів/с**: досягається в `paced`, затримка ~60 мс на 480 |
| 5 | OpenVINO | **Не потрібен зараз** — див. пункти під таблицею |
| 6 | Які ваги зброї оцінювати першими | Див. пункти під таблицею |
| 7 | Севілья — кадри, не відео | Див. пункти під таблицею |
| 8 | Живлення на демо | Лише від мережі, профіль `performance` |

Деталі до рішень:

- **№ 2, `imgsz` 480.**
  - Виміряно: 42–46 мс/кадр, RTF@10 = 0,43–0,50, затримка ~60 мс.
  - Оцінка, не замір: детектор людей на 480 коштує 20–22 мс, тож детектор зброї схожої архітектури додасть
    приблизно стільки ж → RTF@10 ≈ 0,7 із запасом. На 640 вийде ≈ 1,0 без запасу.
  - 416 економить лише 9–14 % проти 480 і знижує покриття позою YOLO11n до 67 %.
  - Детектор зброї, можливо, на 640 через кадр (§6 п. 3) — вирішимо після оцінки ваг.
- **№ 3, YOLO26n.**
  - Швидкість у межах шуму від YOLO11n, а покриття позою на 480 — 80 % проти 74 %.
  - SPEC фіксує лише «nano», тож рішення в межах SPEC, але змінює дефолт конфігу.
- **№ 5, OpenVINO.**
  - RTF@10 ≤ 0,68 навіть на 640 без нього.
  - Резерв (−6…18 %), якщо детектор зброї наблизить RTF до 1.
  - iGPU — лише через `sudo apt install intel-opencl-icd`.
- **№ 6, ваги зброї.**
  - Порядок: (1) cosgun99 YOLO11n; (2) WeaponShield YOLOv8s; запасний — YOLO26n на академічному наборі SOHAS
    (github `0207yjy`, без ліцензії, не завантажено).
  - Оцінювати на кадрах Севільї (CCTV) + валідації.
  - Врахувати конфлікт ліцензій (AGPL-3.0 у чекпойнтах проти заявленої MIT).
- **№ 7, Севілья.**
  - (а) Використати покадрово: вибір ваг і порогу детектора зброї, baseline.
  - Відеосценарій «зброя» перевіряти на XD-Violence Shooting (B2, 104 відео з покадровою розміткою,
    але це фільми/YouTube, не CCTV).
  - Паралельно (б) — запит авторам Севільї на оригінальні відео.
- **№ 8, живлення.** На батареї RTF@10 = 1,54 (640) / 1,02 (480).

- **Замір**:
  - на 4 кліпах Fight (339 кадрів на конфігурацію);
  - із фоновими завантаженнями;
  - серед кліпів лише один 720p, тоді як у RWF 720p/1080p — третина набору.

  Ознаки наступного етапу мають це переживати.

## 11. Як відтворити

```bash
uv sync
uv run pytest                     # 53 тести, без завантаження моделей
uv run ruff check .

# замір (lap — тимчасово, до рішення №1); новий --out для кожного набору кліпів
uv run --with lap sentinel bench --source <кліпи…> --weights weights/yolo26n.pt weights/yolo26n-pose.pt \
    --imgsz 640 480 416 --out results/bench_<назва>.md
uv run --with lap sentinel bench --paced --source <кліпи…> --imgsz 480 --fps 10 --out results/bench_<назва>.md
uv run --with lap --with openvino sentinel bench --format openvino --source <кліпи…> --out results/bench_<назва>.md
```

Дані:
- **RWF:** `curl -L -C - -o RWF-2000.tar.gz https://huggingface.co/datasets/DanJoshua/RWF-2000/resolve/main/RWF-2000.tar.gz`,
  потім `sha256sum` проти LFS-хешу. Розпакування: `tar -xzf … --strip-components=1`; 20 задовгих імен —
  за правилом із `SOURCES.md`.
- **XD-Violence:** перший `curl` на посилання OneDrive з `-c cookies` (отримати cookie сесії), другий — з
  `-b cookies` і `&download=1`.
- **Севілья:** `curl -L -C -` на `weapons_images_2fps.zip` з HF + `sha256sum`.
