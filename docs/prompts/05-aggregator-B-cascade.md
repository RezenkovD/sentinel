## 2. Агрегатор B — `aggregators/llm.py`

- **Вхід** — рівно той `SceneDescription`, що в кеші й у A: канонічний JSON (відсортовані ключі, округлення). Без `aux`, без зображень.
- **Промпт** — версіонований: `PROMPT_VERSION`, текст у `src/sentinel/aggregators/prompts/b_v1.md`. Зміст:
  - роль і задача;
  - словник **кожного** поля з одиницями;
  - **довідка звичайних значень** — p50 / p90 / p99 кожної ознаки на спокійних вікнах **нашого train**
    (скрипт рахує, результат — `prompts/reference_stats.json`, вставляється в промпт).
    Розмічених прикладів не давати: B — zero-shot щодо міток. Записати в `DECISIONS.md` як умову порівняння:
    A навчається на train, B отримує лише статистику спокійних вікон train;
  - рівні: `norm` / `attention` / `alarm`;
  - контракт виходу.
- **`reason_uk`:** ≤ 200 символів, українською, для оператора. Людей називати за номером треку, жодних здогадів про особу.
- **Вихід** — строгий JSON `{risk: 0..1, level, reason_uk}`.
  - Структурований вихід (`json_schema`), якщо провайдер його підтримує для цієї моделі; інакше `json_object`.
  - Валідація pydantic `RiskResult` — разом із відкладеним із сесії 01: `risk` — лише число, не `bool`; порожній `reason_uk` відхиляється.
  - Невалідна відповідь → один повтор із текстом помилки → далі статус `invalid`.
- **Параметри:** `temperature 0`, `seed`, якщо підтримується, обмеження `max_tokens`.
- **Кеш:**
  - ключ — sha256 від версії промпту, моделі, провайдера й канонічного JSON сцени;
  - файл `cache/llm/<модель>/<версія промпту>.jsonl`;
  - зберігати відповідь, токени (вхід / вихід / міркування), затримку, провайдера, час.
- **Ліміти провайдера** (RPM, токени на добу) — з конфігу; на 429 — пауза з backoff.
  - У `live` — відкат на A для цього вікна, із записом у журнал.
  - В експерименті — чекати й повторювати; **ніколи не підставляти A мовчки**: пропущені відповіді рахуються й показуються у звіті.
- **Асинхронний воркер для `live`:** черга ≤ 2, новіша сцена витісняє старішу, тайм-аут 8 с; конвеєр не чекає.
- **Тести з фейковим HTTP:** валідація, повтор, кеш, ліміт, витіснення в черзі, тайм-аут → A.

## 3. Пілот — безкоштовний ліміт, ≤ 300 викликів

- **Вибірка** — лише вікна нашого val, стратифіковано: спокій / бійка, з людьми / без, низький / високий ризик A.
- **Що виміряти:**
  - частку валідного JSON;
  - затримку p50 / p95;
  - токени на виклик (вхід, вихід, міркування);
  - AUC вікон на пілоті;
  - узгодженість: 50 вікон × 3 повтори без кешу — розкид ризику, збіг рівня.
- **У звіт — 10 прикладів `reason_uk` дослівно.**
- **Ітерації промпту** — лише на пілотній вибірці; кожну версію записати.
  Перед будь-яким повним прогоном промпт заморожується як `b_v1`.
- **Бюджет експерименту.** Кількість викликів для кожної конфігурації × токени → сума в $ за поточним тарифом Groq для `gpt-oss-120b`
  (перевір на сайті Groq; на 30.09 — орієнтовно $0,15 / $0,60 за 1 млн токенів вхід / вихід).
  Окремо — час за безкоштовними лімітами Groq і Cerebras. Це піде в рішення, чи поповнювати рахунок.

## 4. Каскад — `aggregators/cascade.py`

- **Правило:** A завжди; B — якщо ризик A ∈ [g_low, g_high] або автомат готовий змінити стан.
  Підсумковий ризик вікна — B, якщо відповідь є, інакше A.
- **`live`:** відповідь B застосовується, коли приходить; автомат ніколи не чекає.
- **Експеримент (з кешу):** у симуляції автомата відповідь B доступна лише через її **фактичну затримку з журналу виклику**
  (вікно t + ⌈затримка⌉), щоб затримка до тривоги була чесною.
- **Сіра зона на val.** Потрібен B на вікнах val.
  - Якщо дозволяють безкоштовні ліміти — увесь val; інакше стратифікована підвибірка ≥ 120 кліпів.
  - Сітка (g_low, g_high) → крива «частка вікон, що пішли в B» проти AUC / F1 епізодів.
  - Обрати точку з ≤ 25 % викликів і найкращим AUC; графік — у `docs/bench/`. Це майбутній рисунок статті.
