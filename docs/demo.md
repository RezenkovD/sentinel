| Де | Що |
|---|---|
| Ліворуч | Термінал 1 — команди `sentinel` |
| Праворуч угорі | Термінал 2 — `scripts/live_view.sh`: рядок на кожне вікно аналізу (≈ 1 с) |
| Праворуч унизу | Telegram Desktop (`telegram-desktop`, уже встановлено) або web.telegram.org — чат із ботом |

`sentinel run` сам у консоль під час роботи нічого не друкує: у ній лише рядок `notifications: TelegramNotifier`
і підсумок наприкінці. Тому все, що відбувається, комісія бачить у терміналі 2 і в Telegram. Приклад рядка:

```
12,0 с  │  людей 8  │  ризик 0,90  │  тривога  │  рішення A  │  ▶ ІНЦИДЕНТ ВІДКРИТО
```

Поля рядка:
- секунда відео;
- людей у кадрі;
- ризик вікна;
- стан автомата: норма / увага / тривога / затихання;
- хто вирішив — A чи B; позначка «запит до B», якщо каскад його покликав;
- «ЗБРОЯ В РУЦІ», якщо хтось тримає зброю;
- події інциденту.

### Крок 1. Прогін на файлі з ботом

```bash
scripts/live_view.sh                                         # термінал 2: чекає на новий запуск
uv run sentinel run --source results/demo/1_fight_src.mkv    # термінал 1 (без --paced)
```

**Що за файл.** `1_fight_src.mkv` — чотири оригінальні кліпи однієї сцени: зал кафе, кліп `JwTPruSFTjk` з нашого
train RWF-2000, послідовність норма → бійка → бійка → норма, 20 с. Склеєно без втрат (FFV1), тож конвеєр бачить
чисті кадри, а не відео з оверлеєм.

**Що бачить комісія.**
- Термінал 2 щосекунди додає рядок:
  - 1–9 с — норма й увага, ризик 0,26–0,80;
  - 10–11 с — увага, 0,78 / 0,76;
  - **12,0 с — «тривога · ▶ ІНЦИДЕНТ ВІДКРИТО»** (ризик 0,90; автомат потребує 3 високі вікна з 5);
  - 14–19 с — затихання;
  - 19,9 с — «■ ІНЦИДЕНТ ЗАКРИТО».
- У Telegram приходить **одне** фото з розмитими обличчями й підписом: «🔴 Ймовірна бійка — Камера 1 · ≈ 8 людей ·
  Активні рухи тіла; швидкий рух поруч з іншою людиною; рух на великій частині кадру · Оцінка: висока · рішення: A».
- Наприкінці те саме повідомлення **редагується** на «✅ Завершено … (8 с) — Камера 1 · кінець відео / потоку».
  Нового повідомлення не приходить: одне повідомлення на інцидент.
- У терміналі 1 — підсумок JSON: 200 кадрів аналізу, 20 вікон, 1 інцидент, RTF.

**Що пояснити:**
- опис сцени раз на секунду, A — логістична регресія на 17 ознаках;
- гістерезис θ_high 0,71 / θ_low 0,65, 3 з 5 вікон;
- тривога о 12-й с, коли бійка вже затихає, — це плата за захист від мерехтіння.

**Перевірено.** Режим без `--paced` детермінований: щоразу ті самі кадри, тривога на 12,0 с, закриття на 19,9 с.
Прогони:
- 10.10 — двічі;
- 11.10 — ще двічі: у режимі A і в каскаді.

Аналіз 20 с відео займає:
- ≈ 13 с від мережі на `performance` (10.10);
- 38 с на батареї, `balanced`, load 4,5 (11.10).

Перед першим запуском ще ≈ 5 с — завантаження моделей.

| Якщо | То |
|---|---|
| Фото не прийшло, а термінал 2 показав тривогу | Немає мережі / Telegram. Сказати про це й показати той самий прогін у консолі: `TELEGRAM_TOKEN= uv run sentinel run --source results/demo/1_fight_src.mkv` — підписи друкуються в терміналі 1. Далі крок 2: у відео повідомлення видно праворуч |
| Термінал 2 мовчить | Він стежить за новим журналом. Якщо запущений після `sentinel run`, то `scripts/live_view.sh --last` |
| Конвеєр не стартує (ваги, OpenVINO) | Крок 2 (відео) і крок 4 (тести); розібратися після захисту |

**З `--paced`** (у темпі камери) ця сцена на межі порога. 10.10 тривога відкрилась:
- `balanced` від мережі — 0 з 2;
- `performance` на батареї — 3 з 5.

На захисті — без `--paced`. Повторний замір від мережі на `performance` — частина Б.

### Крок 3. Вебкамера наживо й команди бота

```bash
scripts/live_view.sh                     # термінал 2
uv run sentinel run --source 0           # термінал 1; Ctrl+C — зупинити
```

У боті по черзі:

| Команда | Очікувана відповідь (з коду; дослівні — після репетиції) |
|---|---|
| `/status` | `Режим: A · RTF 1,00 · <N> кадр/с · відкритих інцидентів: 0 · черга B: 0, зайнятий: ні, витіснено: 0` |
| `/mode cascade` | `Режим: cascade` |
| `/mode A` | `Режим: A` |
| `/mute 1m` | `Нові сповіщення вимкнено на 1m; закриття відкритих інцидентів надходитимуть.` |

**Що бачить комісія.**
- Термінал 2: рядок щосекунди — «людей 1 · ризик … · норма · рішення A».
- Після `/mode cascade` на частині вікон з'являється «запит до B», а коли відповідь приходить — «рішення B».
- Після `/mode A` позначки зникають.

**Що пояснити:**
- **Одна людина перед камерою — це спокій, тривоги не буде, і так має бути.** Провокувати тривогу не треба.
- Каскад кличе B у сірій зоні ризику A (0,50–0,55, обрано на val 11.10), на вікнах УВАГИ й ЗАТИХАННЯ і коли ризик A
  змінив би стан.
- B ніколи не гальмує конвеєр: поки відповіді немає, вирішує A.
- Безкоштовний рівень Groq — 8 000 токенів/хв, а виклик B — ≈ 1 600 токенів. Тому наживо B встигає відповісти на
  ≈ 4 вікна за хвилину, решта вікон іде за A. 11.10 на файлі з кроку 1 в каскаді: 15 запитів до B з 20 вікон,
  4 відповіді (0,7–1,0 с), 10 — «ліміт», рішення за A; тривога й закриття ті самі (12,0 / 19,9 с).
- LLM отримує лише текстовий опис сцени, жодних кадрів.
- RTF у `/status` наживо завжди 1,00, бо камера йде в реальному часі. Показник швидкості тут — кадри/с.

| Якщо | То |
|---|---|
| `camera / stream unavailable` | Закрити інші програми з камерою (браузер, Zoom). Не допомогло — команди бота показати на файлі: `uv run sentinel run --source results/demo/1_fight_src.mkv --paced` (20 с), за цей час `/status` і `/mode cascade` |
| Бот не відповідає на команди | Команди приймаються лише з чату в `TELEGRAM_CHAT_IDS`. Немає мережі — пропустити й пояснити за таблицею вище |
| `/mode cascade` → «Режим не змінено: агрегатор B недоступний (немає ключа API)» | Немає `GROQ_API_KEY` — лишаємось у A. Пояснити каскад на кривій (`cascade_curve.png` з пакета) |
| Позначки «запит до B», але жодного «рішення B» | Вичерпано ліміт Groq (хвилинний або добовий). Так і має бути: вирішує A, конвеєр не стоїть |
| Кадрів/с у `/status` помітно менше за 9 (частота аналізу — 10) | Живлення / профіль / навантаження — див. крок 0 |

### Крок 4. Тести; репозиторій і Docker — на запитання

```bash
uv run pytest -q          # 393 passed (11.10: 26,5 с на батареї під навантаженням)
```

Що є в тестах:
- схема опису сцени;
- ознаки на синтетичних ключових точках;
- A, B (без мережі), каскад;
- автомат інцидентів, команди бота, протокол.

Моделі в тестах не завантажуються.

**Репозиторій:** публічний, ліцензія GNU AGPL-3.0 (через Ultralytics), URL — у звіті 08. Наборів даних, ваг,
відео й ключів у ньому немає.

**Docker** — той самий образ, що в протоколі випробувань:

```bash
docker run --rm -v "$PWD/weights:/app/weights:ro" --entrypoint pytest sentinel:dev -q            # тести в образі
docker run --rm --user "$(id -u):$(id -g)" --env-file .env --device /dev/video0 --group-add video \
  -v "$PWD/weights:/app/weights:ro" -v "$PWD/results:/app/results" sentinel:dev run --source 0     # вебкамера
```

Що робити, якщо не спрацює:
- **pytest впав** — показати, який тест, і не розбиратися на захисті.
- **Docker** — достатньо `docker image ls sentinel` і посилання на протокол 04.10 (`docs/reports/protocol_2026-10-04.md`).
